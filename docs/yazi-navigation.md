# Yazi navigation experiment

The user wants Yazi's fast folder navigation available beside the photo gallery. Native Windows Yazi 26.5.6 is installed on BIGFOOT. Its current CLI exposes `--chooser-file`, `--cwd-file`, `--local-events`, and `--remote-events`.

This is technically feasible. [Yazi's picker mode](https://yazi-rs.github.io/docs/tips/) writes selected file paths for another application, and its [DDS events](https://yazi-rs.github.io/docs/dds/) report `cd` and `hover` changes. Windows [ConPTY](https://learn.microsoft.com/en-us/windows/console/pseudoconsoles) can host a terminal application inside a GUI, but the host must render terminal output, route input, and manage focus and resizing.

The first integration now embeds the installed native Windows Yazi in an `egui_tty` terminal panel backed by ConPTY and Ghostty's terminal engine. It creates a private copy of the user's Yazi configuration for each app session, retaining the user's shortcuts, plugins and themes. Only that copy changes: Yazi's own preview pane is hidden, and image preview/preload plugins are replaced with `noop`. The global Yazi configuration is untouched.

The private `init.lua` subscribes to Yazi's `cd` and `hover` events. It writes the hovered folder (or current folder when hovering a file) to numbered files in a private session directory. The GUI accepts the newest complete report and calls the same `preview_folder` command dispatcher used by the local API. An explicitly opened file remains open when Yazi merely reports that same folder. Opening a path from the toolbar restarts Yazi in that folder. The GUI is still usable without Yazi, and the panel can be hidden with the **Yazi** button. If Yazi quits, **Restart Yazi** starts a new session. This keeps the full Yazi navigation and keymap implementation rather than duplicating it in the photo app.

The pane that owns the keyboard is explicitly labeled. Plain **Tab** is reserved for switching between Yazi and the gallery; the private keymap moves Yazi's default file-information command to **Shift+Tab**. The global Yazi keymap stays untouched. The gallery outlines its keyboard selection, supports all four arrow keys across grid rows, scrolls the selected row into view, and opens the selection with Enter or Space. Switching focus back to Yazi restores its terminal keyboard input.

Tab synchronizes file identity and multi-selection. A private Yazi plugin snapshots its current directory, hovered path, and selected paths. Switching to the gallery selects the matching photo and marks photos in that folder. Gallery Shift+arrows and Shift+click extend a reversible range; switching back sends the cursor and changed marks through per-session file mailboxes. Snapshot, navigation, sort-order and theme requests also use this paired transport, independent of Windows' shared DDS listener. Requests are published by atomic rename and claimed before reading. The Yazi action clears only marks in its current directory, so marks in other directories survive. If gallery marks did not change, Tab sends only the cursor and leaves Yazi's global selection intact. `photo-cli ctl focus-gallery`, `focus-navigator`, `select-path`, `extend-selection`, and `mark` use the same dispatcher. The local API protocol is v3. A Yazi action still performs file operations under Yazi's own rules; Photo Workshop observes the result through its folder watcher and does not provide undo for those actions.

BIGFOOT regression after the first v2 installation: Yazi itself launched from the shortcut, but `focus-gallery` returned `program not found` because the GUI process could not resolve the separate `ya.exe` DDS client. The terminal test had inherited a different PATH from the build shell and missed this. The pane now resolves `yazi.exe` and its sibling `ya.exe` together, with a WinGet installation fallback, and uses those absolute paths for every launch and DDS call. A test deliberately removes PATH from the lookup to cover the installed-shortcut environment.

The next installed build revealed a latency regression: Tab took 5–9 seconds even with only 20 photos. On the same folder, `Gallery::open` took 48 ms and listing took 27 ms, so file lookup was not the bottleneck. The GUI had no console and launched the console-based `ya.exe` for each DDS request. The calls now use Windows `CREATE_NO_WINDOW`. A hidden Release process controlled through the local API then measured `focus-gallery` at 152/65 ms and `focus-navigator` at 68/72 ms. This verifies the live command path on the small folder, not the appearance or latency of a large cloud library. No filesystem indexer was added; cursor synchronization already uses the full file path.

The terminal dependency requires Zig 0.15.x during builds. Add your Zig 0.15.2 installation to PATH.

The terminal background also fills the fractional margin outside its complete character cells, preventing a different panel color from appearing as narrow strips at the edges. This is a rendering fix; the user's screenshot should confirm whether it addresses every visible artifact.

`cargo test --workspace` includes a native ConPTY smoke test: it launches the installed Yazi, answers terminal queries through `egui_tty`, and verifies folder reporting, cursor and mark transfer, Space selection in Yazi, and preservation of marks in another directory. The user will inspect the GUI itself; this test does not claim visual verification. The current folder is watched for external file changes and the gallery rescans it. Yazi's own file operations remain available under the user's keymap, but they are outside the photo workshop's future command journal and undo contract. The private TOML config is parsed and modified with `toml_edit`, preserving the user's comments and unrelated settings; clean-machine and unusual-config checks remain useful.

The terminal dependency requires Zig 0.15.x during builds. Add your Zig 0.15.2 installation to PATH.

## Sort and pointer checkpoint

The private Yazi keymap appends `plugin workshop-sync order` to its sort actions, including the user's Cyrillic bindings. The plugin reads `cx.active.current.files` in Yazi's own order, writes a numbered report, and the gallery applies it through the `set_order` command. The gallery matches Yazi's ordinary Windows paths to its canonical folder without stat-ing every file. It retains the current photo, cursor, marked paths, and cached textures by file identity. `list_order` exposes the effective order through the live API. A folder refresh retains the last order for existing files while waiting for Yazi's next report. The app does not provide separate sort buttons.

Escape in the gallery grid calls `set_marked` with an empty list; the next Tab transfers that cleared selection to Yazi. In photo view, Escape still returns to the grid. The embedded `egui_tty` version handles text selection but does not forward pointer buttons to the PTY, so the pane emits SGR mouse reports for clicks. A left click moves Yazi's cursor; a GUI double click sends `l` after the click so a folder opens. Mouse 4 and Mouse 5 over the terminal send Yazi's `H` and `L` history commands and focus the terminal. The native ConPTY fixture checks click, double-click navigation, history back/forward, and reverse alphabetical sort reporting. Wheel scrolling in the embedded terminal is still handled by `egui_tty` as terminal scrollback rather than Yazi navigation.
